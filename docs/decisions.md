## ADR: Лицензирование кода и контента

- **Контекст:** репозиторий вырос из шаблона github-slideshow (MIT, © Thomas Friese, 2016) и переписан в генератор семейного архива (2026).
- **Решение:** сохранить MIT для кода с двумя copyright-строками (Thomas Friese + Smaturus); контент `content/` и генеалогические тексты — all rights reserved, без открытой лицензии; ПДн живых людей не коммитятся.
- **Последствия:** код можно форкать и переиспользовать; тексты и данные защищены; атрибуция исходного шаблона сохранена.

## ADR: Архитектура репозиториев и переименование

- **Контекст:** имя github-slideshow досталось от шаблона и не отражало суть проекта. В перспективе экосистема разделится на хаб и дочерние ветви: family-history (общий семейный архив), skiba-history (ветвь Скиба), matyukhin-history (ветвь Матюхиных).
- **Решение:** репозиторий переименован в family-history. Сейчас он содержит весь код и контент и позиционируется как зонтичный проект (хаб); разделение на отдельные репозитории отложено до появления практической необходимости.
- **Последствия:** URL сайта — https://smaturus.github.io/family-history/; ссылки на репозиторий в документации обновлены (упоминания github-slideshow как имени исходного шаблона в LICENSE и ADR сохранены намеренно). Впоследствии на главной странице family-history появятся ссылки на дочерние проекты. GitHub сам перенаправляет со старого имени репозитория, но полагаться на это не стоит.

## ADR: Статус древа без «Подтверждено»

- **Контекст:** плашка «Подтверждено» на карточках древа означала лишь наличие записи в GEDCOM-выгрузке MyHeritage, а не документальное подтверждение; при этом предки, установленные по ревизии 1834 г. (село Мокрое), помечены «Гипотеза» — иерархия статусов читалась наоборот, самый «сильный» ярлык соответствовал самому слабому доказательству.
- **Решение:** плашка дефолтного статуса (`ok`) убрана из `render_badge` и из легенды древа. Карточка без плашки = «есть в базе MyHeritage», легенда объясняет это явно («запись базы не является документальным подтверждением»); цвет рамки (сталь) сохранён. Точечные статусы «Гипотеза» и «Нет данных» не менялись. Текущий `index.html` приведён к этому виду механической трансформацией (см. ADR «Механическая трансформация артефакта») с проверкой эквивалентности данных.
- **Последствия:** слово «Подтверждено» больше не используется на сайте; ключ `tree.status.ok` в `content.yaml` сохранён (валидация схемы требует ok/hyp/q). После появления GEDCOM обычная пересборка воспроизведёт новый вид древа без ручных правок.

## ADR: Механическая трансформация артефакта

- **Контекст:** a11y-правки (SVG title/desc, tabindex, aria-current, reduced-motion) нужно было опубликовать на live-сайте, но GEDCOM в данный момент недоступен, а боевой `index.html` собирается только локально — полноценная пересборка невозможна.
- **Решение:** правки применены к существующему `index.html` побайтовой трансформацией (коммит `19a4cc1`) с доказательством эквивалентности данных: извлечение и сравнение имён (SVG `<text>` + таймлайн) и всех 4-значных годов до и после — мультимножества совпали один в один (266 вхождений годов, 32 имени). Генератор (`build_site.py`) уже содержит те же a11y-изменения, поэтому при появлении GEDCOM обычная локальная сборка воспроизведёт этот же результат, и трансформация станет обычным ребилдом.
- **Последствия:** live-сайт получил a11y-правки без пересборки; риск расхождений с будущей генераторной сборкой закрыт сверкой и идентичностью правок в генераторе. Метод подходит только для точечных, механически проверяемых изменений — любые содержательные правки данных через ручную правку HTML запрещены.

## ADR: Legacy hero-кода

- **Контекст:** в `scripts/build_site.py` остался блок ~870 строк (строки 959–1826: `_hero_limbs`, `_hero_facet_points`, `_hero_density`, `_hero_glow`, `_hero_veil`, `_hero_defs`, `render_hero_graph`) — процедурный SVG-генератор «созвездия» для первого экрана. `render_hero_graph` больше не вызывается: hero рендерится статически (`render_hero_section` поверх мастер-арта `Image 1.png` по раскладке `Image 2.png`, см. таблицу «Hero / первый экран»).
- **Решение:** код оставлен как legacy — возможно, пригодится для будущих экспериментов с дизайном (процедурные варианты фона без перерисовки арта). Он задокументирован здесь, чтобы новые контрибьюторы не принимали его за живой путь сборки и не тратили время на «мёртвую» ветку.
- **Последствия:** функция `render_hero_graph` и её хелперы не покрыты тестами и не влияют на CI; при рефакторинге `build_site.py` их можно удалить одним движением, не ломая ничего. Перед любым повторным использованием — ревизия и покрытие тестами.

## ADR: CI-сборка на фикстуре

- **Контекст:** реальный `data/skiba.ged` содержит ПДн живых людей и не может передаваться в Actions, поэтому сборка в CI изначально не выполнялась (см. «Данные и сборка») — поломки генератора обнаруживались только при локальной сборке, а инструменты ассетов (numpy, Pillow) вообще не были зафиксированы.
- **Решение:** CI (`ci.yml`) прогоняет `build_site.py` на синтетической фикстуре `tests/fixtures/minimal.ged` с вымышленными людьми, включая якорные ID `@I155@`/`@F59@`, чтобы выполнялся и inject-блок архивных предков. Реальные данные по-прежнему в CI не попадают; боевой `index.html` собирается и коммитится локально. numpy и Pillow вынесены в `requirements-dev.txt` — сборщику они не нужны. Входные файлы проверяются до разбора: наличие, UTF-8, записи INDI — с понятными сообщениями вместо трейсбеков.
- **Последствия:** поломки сборки и генератора ловятся в CI до merge; ADR «Сборка локальная» уточнён, но не отменён — в CI остаётся фикстура, не реальные данные. Фикстуру нужно поддерживать при изменении контракта якорей (тесты парсера — следующий шаг).
