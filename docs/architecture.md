# Архитектура и инженерные решения

Описание данных, сборки и публикации семейного архива. Краткий обзор — в [README](../README.md); решения и исследовательские задачи ведутся локально и в репозиторий не входят.

## Схема сборки

```
data/family.yaml       ──►  parse_data.py  ──┐
  (локально, не в Git)      (модель,           │
                             валидация)         ├──►  build_site.py  ──►  index.html
content/content.yaml ──────────────────────────┘         ▲
assets/site.css      ────────────────────────────────────┘

index.html + .nojekyll + assets/hero-bg*.{avif,webp,jpg}
                  ──►  статическая публикация
```

| Слой | Источник | Ответственность |
|------|----------|-----------------|
| Данные | `data/family.yaml`, `scripts/parse_data.py` | Персоны, даты, родственные связи, семьи, статусы и проверка приватности |
| Контент | `content/content.yaml` | Два семейных раздела, краткие тексты, документы, указатель мест, дополнительные сведения для карточек, хроники и списки фотографий |
| Генератор | `scripts/build_site.py` | Два отфильтрованных SVG-древа, секции, навигация, встраивание CSS и проверка HTML |
| Публикация | `.github/workflows/pages.yml` | Копирование только разрешённых статических файлов |

## Единая база и два представления

`data/family.yaml` остаётся единственным источником генеалогических фактов. Физического разделения базы нет. В `content/content.yaml` разделы `sections.matyukhiny` и `sections.skiba` ссылаются на корневых супругов из `meta` и задают собственные идентификаторы страниц и древ.

`resolve_family_context()` выбирает корневую семью. `render_pedigree_svg()` строит предков только выбранного супруга (`include_spouse_ancestors=False`), сохраняя второго супруга и общего ребёнка якорями обоих представлений. У каждого SVG собственный `id_prefix`, заголовок и описание. Поэтому одна и та же связь хранится один раз, а состав видимых предков различается.

Поиск в основной навигации охватывает всех опубликованных людей: записанные формы имён и фамилий и публичные даты. Заметки, места и точные даты живых в индекс не входят. Поиск внутри древа, масштаб, вписывание, исходный вид, перемещение и жест двумя пальцами сохранены. Масштаб меняет только SVG внутри `.treewrap`. Цвета карточек древа заданы литералами sRGB и не зависят от CSS-переменных. Класс `hyp` следует полю `status`, а не форме или отсутствию даты; `unknown` и `approx` описывают только даты.

Четыре основные ветви распределены по фактическим связям:

- «Матюхины»: `matyukhin_father` и `astafyev_mother`;
- «Скиба»: `skiba_father` и `potashkin_mother`.

Две неродственные семьи Алексеевых представлены отдельно в разделе «Скиба» и не объединяются.

Каждый раздел открывается короткой шапкой и ведёт в пять самостоятельных частей: «Ветви», «Древо», «Люди», «Документы» и «Места». Текущий пункт внутреннего меню визуально выделен и размечен `aria-current="page"`. Описания ветвей содержат только линию, основные фамилии и необходимые исследовательские особенности; две неродственные семьи Алексеевых поясняются отдельно. Указатель мест раскрывает связанные персоны и документы без биографических описаний пунктов. Дополнительные места из прежних редакционных примечаний привязаны к id персон в `content/content.yaml` и из этого же источника выводятся в карточках. Обычная биографическая хроника остаётся в исходном `content/content.yaml`, но не публикуется отдельной страницей; прежние адреса `-timeline` сохранены как якоря-совместимости на разделе документов. `gallery.photos` зарезервирован для настоящих семейных фотографий; при пустом списке `render_family_gallery()` не создаёт ни секцию, ни ссылку в навигации. Главная содержит только утверждённый первый экран, абзац об основателе и два равнозначных входа.

Внутренние ссылки используют идентификаторы `#matyukhiny`, `#skiba`, `#matyukhiny-tree`, `#skiba-tree`, а также суффиксы `-branches`, `-people`, `-sources` и `-places`. Прежние `-timeline` ведут к документам соответствующего раздела. Карточка персоны — панель по якорю `#person-<id>` существующего идентификатора; адрес не зависит от имени. Пустые поля не выводятся. Поле `note` и техническая метка `source` не публикуются: в записи это служебная строка с точной датой, в том числе у живых. Фотографии и воспоминания в модели не публикуются. Имена опубликованных родственников ведут на их карточки. «Показать в древе» открывает семейный раздел, ставит масштаб 100% и выделяет персону. В список персон раздела входят кровные родственники якоря и их супруги, в том числе те, кого нет на древе предков. Запись без родственной цепочки к якорям в публичные страницы не попадает. Древа помечены `page2` и `page3`; эти идентификаторы проверяются сборочным тестом.

## Документы и редакционный слой

Архивные результаты и семейные сведения различаются полем `kind` у документов. Гипотезы не становятся утверждениями: связь семьи из ревизской сказки 1834 года с позднейшими Матюхиными явно требует подтверждения. Реквизиты уже найденного документа сохранены в `content/content.yaml`; связанные персоны ведут в карточки. Архивные направления не публикуются и остаются в локальном `docs/research-tasks.md`; генератор не выдумывает реквизиты.

Публичные статистические отчёты, пояснения обработки, список исследовательских пробелов и дублирующая древо цепочка поколений не выводятся. Исследовательские задачи находятся в локальном `docs/research-tasks.md`. Этот файл и `docs/decisions.md` исключены из Git. Факты, пробелы и расхождения в `data/family.yaml` при этом не изменяются.

## Приватность

`parse_data.py` отклоняет точные даты и места рождения ныне живущих. Публичные значения возвращаются через `public_years` и `public_place`; при отсутствии данных о смерти человек считается живым. Построенный HTML дополнительно проверяется на точные даты живых.

Реальный `data/family.yaml` целиком исключён из Git. В репозитории и CI используется синтетическая `tests/fixtures/minimal.yaml` с вымышленными людьми. Предупреждение о правиле публикации выводится один раз в подвале сайта.

## Тесты и CI

В `tests/` находятся 29 pytest-проверок загрузчика, ссылок, приватности, поиска, доступности SVG и встроенной навигации. Интеграционная сборка на фикстуре требует ровно два SVG-древа и оба идентификатора `page2`/`page3`.

Workflow `.github/workflows/ci.yml` запускает тесты, подставляет фикстуру вместо локальных данных, пересобирает сайт и отдельно проверяет наличие двух древ. Реальные данные в Actions не передаются.

## Статическая публикация

Allowlist `.github/workflows/pages.yml` не расширяется: `index.html`, `.nojekyll` и `assets/hero-bg{,-768,-1280}.{avif,webp,jpg}`. CSS встраивается в HTML. Мастер-фон и референс раскладки не публикуются; отдаются только существующие производные фона.

Файл `.nojekyll` — флаг статической публикации: готовый `index.html` и разрешённые ассеты отдаются без дополнительной обработки. Локальная сборка ничего не отправляет в сеть. Публикация требует отдельного решения владельца и настроенного репозитория.

## Структура репозитория

| Путь | Назначение |
|------|------------|
| `data/family.yaml` | Локальная единая база, не входит в Git |
| `content/content.yaml` | Тексты и структура двух семейных разделов |
| `scripts/parse_data.py` | Модель данных, ссылки и приватный фильтр |
| `scripts/build_site.py` | Генерация HTML и двух представлений древа |
| `scripts/extract_data.py` | Миграционный инструмент; обычная сборка его не запускает |
| `assets/site.css` | Существующая визуальная система и компоненты разделов |
| `assets/Image 1.png` | Неизменяемый мастер фона первого экрана |
| `assets/Image 2.png` | Референс композиции первого экрана |
| `assets/hero-bg*` | Существующие производные фона для статической публикации |
| `index.html` | Собранный сайт, синхронизированный с исходниками |
| `docs/research-tasks.md` | Локальные исследовательские задачи, не входит в Git |
| `tests/` | 29 проверок и синтетическая фикстура |
| `.github/workflows/ci.yml` | Тесты и контрольная сборка без реальных данных |
| `.github/workflows/pages.yml` | Прежний механизм и allowlist публикации |
