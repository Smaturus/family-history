# Архитектура и инженерные решения

Подробное описание слоёв данных, сборки и публикации семейного архива. Краткий обзор — в [README](../README.md); фиксированные решения — в [decisions.md](decisions.md).

## Схема сборки

```
ревизская сказка 1834 г. (снимки страниц, вне репозитория):
чтение (OCR + ИИ), проверка ─┐
                             ▼
data/skiba.ged          ──►  parse_gedcom.py  ──┐
  (локально, не в Git)                          ├──►  build_site.py  ──►  index.html
content/content.yaml    ────────────────────────┘         ▲
assets/site.css         ──────────────────────────────────┘
                                                          │
merge в master ──► GitHub Actions ──► gh-pages ──► GitHub Pages
                                      (только index.html, .nojekyll
                                       и assets/hero-bg*.{avif,webp,jpg})
```

| Слой | Источник | Ответственность |
|------|----------|-----------------|
| **Данные** | `data/skiba.ged` + `scripts/parse_gedcom.py` | Имена, даты, связи, статистика, фильтрация приватности; вставка предков по архивным документам вне GEDCOM |
| **Контент** | `content/content.yaml` | Заголовки, абзацы, очерки линий, подписи, легенда |
| **Генератор** | `scripts/build_site.py` | Модульный рендер секций, SVG-древо, валидация YAML, post-build проверка приватности |
| **Публикация** | `.github/workflows/pages.yml` | Деплой только статических файлов в `gh-pages` |

## Источники данных

Опубликованные сведения складываются из трёх слоёв. Слои различаются способом получения и степенью доказанности, поэтому разделены и в коде, и в подаче на сайте.

**1. Структурированная основа — GEDCOM.** `data/skiba.ged` — локальный экспорт семейного древа в формате GEDCOM 5.5.1; типичное происхождение файла — выгрузка проекта MyHeritage. Это основной машиночитаемый вход: `scripts/parse_gedcom.py` берёт из него персоны, даты, места и родственные связи, а `build_site.py` считает по ним статистику, таймлайн поколений, ономастику и географию. MyHeritage — только источник файла, а не удостоверяющая инстанция: ссылки внутри экспорта в основном ведут на Smart Match, то есть на деревья других пользователей, а не на архивные документы.

**2. Архивные дополнения.** Часть предков установлена вне выгрузки, по постранично отснятым архивным делам — прежде всего по ревизской сказке 1834 года по селу Мокрое Белевского уезда Тульской губернии (двор №26). Распознавание скорописи и сопоставление записей выполнялись с помощью ИИ (OCR и разбор рукописного текста); прочтения проверялись вручную и лишь затем кодировались в сборку:

- **персоны и связи** — программной вставкой в `scripts/parse_gedcom.py` (блок «Inject … from the 1834 Revision List»). Илья Матвеев, Григорий Ильин, их жёны и дети создаются в модели данных с собственными идентификаторами (`@I_MOKROE_*`, `@F_MOKROE_*`), а Федот (`@I155@` в GEDCOM) переподключается к найденным родителям. Сам `data/skiba.ged` при этом не правится.
- **формулировки и оговорки** — текстами в `content/content.yaml`: очерк линии Матюхиных с реквизитами дела, примечания к фамилиям и местам, легенда «подтверждено / гипотеза / нет данных».

ИИ и OCR здесь — исследовательский инструмент чтения источника, а не самостоятельный источник и не автор выводов. Чтения, не подтверждённые документом, помечены на сайте как гипотезы; фамилия Матюхин для поколений 1834 года сознательно не утверждается, потому что в ревизии она не записана.

**3. Редакционный слой — YAML.** `content/content.yaml` отвечает за подачу: заголовки, вводные абзацы, очерки линий, примечания, подписи и легенду. Числа, даты и цепочки поколений в нём не дублируются — их считает генератор из слоёв 1 и 2.

Правила приватности применяются к первому слою. Вставленные архивные персоны — люди XVIII–XIX веков, под ограничение не попадают.

### Замена GEDCOM: что происходит с архивными поколениями

Вставка архивных предков выполняется **в коде, после разбора GEDCOM**, поэтому при замене `data/skiba.ged` новым экспортом MyHeritage ничего вручную не переносится. Механика (блок «Inject … from the 1834 Revision List» в `scripts/parse_gedcom.py`):

1. Персоны Илья Матвеев, Григорий Ильин, их жёны, дети и семьи создаются заново при каждой сборке с идентификаторами `@I_MOKROE_*` / `@F_MOKROE_*` — они не зависят от содержимого экспорта.
2. Федот (`@I155@`) обогащается данными ревизии 1834 года (имя, место, «ABT 1818», отметка о смерти) — эти значения перезаписывают то, что сказано в экспорте: документ считается авторитетнее выгрузки.
3. Его родительская связь переключается с гипотетической (`@F59@` / безымянный `@I163@`) на архивную семью Григория и Степаниды; ссылка на Федота в `@F59@` удаляется, чтобы предок не считался дважды.

**Якоря и их риск.** Вставка привязана к идентификаторам исходного экспорта: обогащение Федота выполняется только при наличии `@I155@` в новой выгрузке. Если будущий экспорт перенумерует ID, архивные персоны по-прежнему будут созданы, но останутся не привязанными к прямой линии — линия обрежется на прежнем месте, и древо/таймлайн молча потеряют поколения 1834 года. Сборка при этом не падает. Поэтому после замены GEDCOM нужно проверить на собранном сайте цепочку Илья → Григорий → Федот в линии Матюхиных; якоря `@I155@`/`@F59@` зафиксированы в CI-фикстуре `tests/fixtures/minimal.ged` и покрыты тестами парсера (`tests/test_parser.py`).

## Инженерные решения

**Privacy-by-design.** GEDCOM не хранится в репозитории (`.gitignore`). Для ныне живущих на сайте публикуются только имя и год рождения; точные даты, места и контакты отфильтровываются в `parse_gedcom.py`. Логика приватности детерминирована (опирается на дату экспорта GEDCOM, а не на текущее время) и защищена сквозной валидацией: сборка падает, если в итоговый HTML утекли точные даты живых людей. Принцип fail-safe: если год рождения неизвестен и нет отметки о смерти, человек по умолчанию считается живым и скрывается от публикации.

**Разделение данных и текстов.** GEDCOM и проверенные архивные дополнения формируют факты в Python, а `content/content.yaml` содержит только редакционные тексты без `{плейсхолдеров}`. Архивные персоны добавляются отдельным кодовым слоем, поэтому исходный GEDCOM можно заменить новым экспортом без ручного редактирования.

**Валидация YAML.** `build_site.py` проверяет обязательные ключи и типы в `content/content.yaml` и падает с понятным сообщением, если структура нарушена.

**Тесты и CI.** Логика парсера (включая вставку архивных предков 1834 года и фильтр приватности) и a11y собранного HTML (SVG title/desc, tabindex, aria-атрибуты, reduced-motion) покрыты pytest-тестами в `tests/` (14 тестов). Workflow `ci.yml` прогоняет их при каждом push/PR в `master`, затем выполняет smoke-сборку сайта на синтетической фикстуре `tests/fixtures/minimal.ged` с вымышленными людьми и проверяет целостность вывода. Подробнее — ADR «CI-сборка на фикстуре» в [decisions.md](decisions.md).

**Безопасная публикация.** Workflow публикует в `gh-pages` только allowlist: `index.html`, `.nojekyll` и производные фона первого экрана `assets/hero-bg{,-768,-1280}.{avif,webp,jpg}`. CSS инлайнится при сборке; исходный **hero background** (`assets/Image 1.png`) в Pages не попадает — отдаются только сжатые responsive-варианты, а не base64 и не исходный PNG. GEDCOM, YAML, Python-скрипты и исходные изображения на live-сайт не уходят.

**Ассеты первого экрана.** Фон — мастер `assets/Image 1.png`; раскладка заголовка, навигации и дат сверстана по референсу `assets/Image 2.png`. В прод уходят только производные AVIF → WebP → JPEG (ширины 768 / 1280 / 1376) с preload LCP-кандидата.

**Осознанный trade-off.** Боевая сборка выполняется локально: GEDCOM содержит персональные данные и остаётся на машине. CI прогоняет `build_site.py` только на синтетической фикстуре с вымышленными людьми (`tests/fixtures/minimal.ged`), чтобы ловить поломки генератора до merge; реальный GEDCOM в Actions не попадает. Перед merge в `master` обновлённый `index.html` по-прежнему коммитится вручную после локальной пересборки.

## Публикация

После merge в `master` workflow [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) автоматически обновляет `gh-pages`.

**Требования к репозиторию (один раз):**

- `Settings` → `Actions` → `General` → **Read and write permissions** для workflow
- Ветка `gh-pages` не должна блокировать force-push от GitHub Actions

Файл `.nojekyll` отключает обработку Jekyll на GitHub Pages и нужен, чтобы статический `index.html` и ассеты отдавались как есть.

## Структура репозитория

| Путь | Назначение |
|------|------------|
| `data/skiba.ged` | GEDCOM-экспорт (основной источник данных), локально, в Git не попадает |
| `content/content.yaml` | Редактируемые тексты сайта |
| `scripts/parse_gedcom.py` | Парсер GEDCOM, модель персон, фильтрация приватности, вставка предков по архивным находкам (ревизия 1834 г.) |
| `scripts/build_site.py` | Генератор `index.html`: `render_*` секции, валидация YAML, post-build проверка |
| `assets/site.css` | Стили (инлайнятся в HTML при сборке) |
| `assets/Image 1.png`, `assets/Image 2.png` | Мастер фона первого экрана и референс раскладки (в Pages не публикуются) |
| `assets/hero-bg*.{avif,webp,jpg}` | Оптимизированные производные фона первого экрана — входят в allowlist `gh-pages` |
| `index.html` | Собранный сайт (коммитится в `master`) |
| `tests/` | pytest-тесты (парсер, приватность, a11y) и синтетическая фикстура `minimal.ged` |
| `requirements.txt` | Рантайм-зависимости сборщика |
| `requirements-dev.txt` | Зависимости разработки: pytest, numpy, Pillow |
| `.github/workflows/ci.yml` | Тесты + smoke-сборка на фикстуре при push/PR |
| `.github/workflows/pages.yml` | Автопубликация в `gh-pages` |
| `.nojekyll` | Отключает обработку Jekyll на GitHub Pages |
